Beginner's Guide

The Wiki as an External Brain:
Taming Complex Projects with a Knowledge Network

A person's working memory can handle only 4–7 items at once. But a robot control system has hundreds of tightly coupled technical details: coordinate frame conventions, safety stop protocols, SDK parameter semantics, IK solution variants, and more.

You don't need to keep all of this in your head. Crystallise it into an interconnected knowledge network: at any moment you only need to focus on the current node, while the wiki and the AI agent look after the rest. This isn't laziness. It's putting human cognitive bandwidth where judgement is actually needed.

I Core Idea: You Only Need to Focus on "One Point"

Imagine you're repairing a car. You don't need to understand every detail of the engine, gearbox, electrical system, and suspension at once. You only need to know: right now I'm working on the brake pads, and if I need to know how the brake line connects to the ABS module, there's a service manual with a chapter I can turn to.

This wiki system does exactly that, but for Human-AI collaborative development:

Without a Wiki

You have to keep every key constraint of the whole system in your head. Forget a safety rule? The agent will happily write code that breaks it. Forget the precise meaning of a term? The agent will invent one of its own.

With a Wiki

You only need to focus on the current task. Safety constraints, term definitions, and settled decisions are all captured in wiki nodes. When work begins, the agent automatically loads the relevant nodes per protocol. You make the high-level judgements; the details go to the wiki and the agent.

A Knowledge Network, Not a Pile of Documents

Traditional documentation is linear: one piece after another, and you need to read the previous one to understand the next. This wiki is networked: each piece of knowledge is an independent node, and nodes are linked by references. You can enter from any node and follow the connections to the context you need.

The interactive diagram above shows a fragment of the knowledge network from the FR5-StreamingSys project. Hover over any node to see its connections. You don't need to understand every node, you only need to know that "when I'm working on something IK-related, the Boot Matrix will route me to the right nodes."

What reducing complexity really means: it isn't about making a complex system simple (it's inherently complex), it's about reducing the amount you need to understand at once from O(n) to O(1). You focus on one node at a time, and neighbouring nodes are expanded by the wiki and agent as needed. It's like virtual memory in an operating system: physical memory is limited, but on-demand paging lets a process use an address space far larger than physical memory.

Humans Make Judgements, the Agent Handles the Details

This system redraws the boundary of responsibility between human and agent:

Human (High-Level)Wiki + Agent (Detail Layer)
Plan Decide "what to do" and "why" Check whether the plan conflicts with settled decisions or breaks safety rules
Implement Review key design choices Load context per the Boot Matrix, write the code, follow CLAUDE.md discipline
Review Judge whether review findings need fixing Pull safety rules and term definitions from the wiki, adversarially review the code
Solidify Decide which lessons are worth solidifying Turn lessons into rules, update the Glossary, update the Boot Matrix

The key point: you don't need to remember the difference between StopMove and StopMotion. You only need to know that "stopping the machine is a delicate matter." When the agent does related work, it automatically loads the precise distinction and the prohibitions from ctx_safety/. Your attention stays entirely on questions that genuinely need human judgement, like "what should this feature's user experience be like."

II Wiki Structure: Five Layers of Knowledge, Loaded on Demand

The nodes in the knowledge network aren't flat, they're layered by authority. Information closer to the code and the hardware carries higher authority:

0
CLAUDE.md
Auto-loaded every time — the behavioural constitution
1
AgentMgmt (005)
Glossary, Safety, Boot Matrix, Truth Ladder
2
Architecture (002)
System architecture + settled.md decisions
3
Inbox (001) + Guides (003)
Working notes + operational guides
4
_historical/
Superseded documents — for archaeology only

The point of layering: when two nodes disagree, you don't need to judge which is right yourself, the Truth Ladder tells you directly. Code > safety rules > contracts > design docs > notes. This is one more thing offloaded from your head.

Core Mechanism: Boot Matrix Routing

The Boot Matrix is the "routing table" of the knowledge network. When the agent receives a task, it looks up the table to find which nodes to load, which code files to read, which tests to run, and which stale files it should not read.

For example, when you say "I want to modify the IK solver," the Boot Matrix tells the agent:

Must readFollow-up readingCode anchorsDeprecated, do not use
ctx_safety/offlineIK...Safety.md ctx_offline_ik/offlineIKCurrentPipeline.md core/path_ik_resolve.py _historical/offlineIKIntegration*

You don't need to remember these routes, you don't even need to know the Boot Matrix exists. You only need to say "modify the IK," and the agent knows what to read on its own.

III Workflows in Practice (Three Full Examples)

The three examples below show how the wiki is used in day-to-day development. Notice throughout: the human is always making high-level judgements, while detail checks are offloaded to the wiki and agent.

Example One: Proposing a Plan + Adversarial Plan Review

PLANREVIEW Scenario: adding a "resumable pause" feature to the robot, so a print can be paused mid-way and then continued.

You Say

Step One — Stating the Requirement
You
"I want to be able to resume printing after a pause. Right now the only option is ESTOP and starting over, which is wasteful."

Note: you only stated the intent, not how to implement it. The agent's job is to load the constraints from the wiki, then design a solution within them:

Knowledge Nodes the Agent Loads Automatically
Agent
Checks the Boot Matrix → the "ESTOP / NewSpline Runtime" row

Loads 3 nodes:
• GLOSSARY.md — confirms the precise semantic distinction between Hard ESTOP / Recoverable Pause / PauseMotion
• ctx_safety/estopStopMoveLesson.md — stopping must use StopMove; calling NewSplineEnd() before an ESTOP is forbidden
• settled.md S1.1 — DO switching must block and wait

The design can now proceed.

What the wiki did here: you didn't need to remember a detail like "NewSplineEnd() waits for the segment to finish." But if the agent didn't know this constraint, it would design a plan to "gracefully finish the current trajectory before pausing," which sounds reasonable but would actually mean pressing pause and the robot not stopping. The wiki prevented this mistake without you having to worry about it.

After the Agent Writes the Plan: Adversarial Review

A plan isn't executed the moment it's written. Adversarial review means a different agent (or the same agent in a different role) is tasked specifically with finding faults, checking whether the plan breaks safety rules, conflicts with settled decisions, or uses terminology incorrectly.

Adversarial Review Finds Issues
Agent
Issue 1 (safety violation): the plan locates the resume point using the index of a Python-side deque. But GLOSSARY.md #4 clearly distinguishes the Preview Queue (Python side) from the Robot Controller Buffer (hardware side): the two count independently and are not synchronised. The resume point must be based on the actual TCP pose.

Issue 2 (conflicts with settled.md): the plan proposes waiting asynchronously for the DO switch. settled.md S1.1 requires a blocking wait, a hardware constraint.

Your role: look at the review findings, judge whether they're valid, and approve the changes. You don't need to check what settled.md actually says yourself, the agent has done the cross-checking for you.

Example Two: Implementation + Adversarial Code Review

CODEREVIEW Once the plan review passes, implementation begins.

What Happens While the Agent Writes Code

You don't need to tell the agent to "remember to read the safety rules," the Boot Matrix has already configured the routing. Before writing a single line of code, the agent automatically loads:

  • Safety rules (ctx_safety/) — use StopMove for stopping, not StopMotion
  • System architecture (ctx_motion_streaming/) — understanding NewSpline's threading model
  • Code anchors — knowing which files to change
  • Deprecated documents — knowing not to reference the old active-chunk approach

Adversarial Code Review

Once the code is written, code review begins. The review agent is independent of the implementation agent and loads the same wiki nodes from scratch:

Code Review Findings
Agent
Finding 1 (safety violation): line 87 uses robot.StopMotion() as the first call when stopping. The ctx_safety hard rule requires the first action to be emergency_stop_motion() (via the StopMove 8080 control channel).

Finding 2 (performance violation): line 142 calls resolve_stamped_gcode_path() inside the UI draw() loop. The CLAUDE.md Render-Loop Rule forbids file I/O in the per-frame UI loop; state should be read from cache instead.

Your role: look at both findings, judge their severity, and approve the fixes. You don't need to go hunting for rules in ctx_safety yourself, the review agent has already made the connection.

The key feeling: throughout the whole process, your attention stays on the high-level question of "is this feature correct." SDK parameter semantics, control channel protocols, UI rendering performance constraints, all of these details are held by the wiki. You don't need to carry them all in your head at once.

Example Three: Wiki Updates and Knowledge Solidification

WIKISOLIDIFY During development you learn something new, for example the discovery that "the Python queue position and the hardware buffer aren't synchronised." If you don't solidify it, this knowledge is lost the next time a related task comes up.

The Solidification Loop

Discovery / Fault
→
Postmortem
→
Distil a Rule
Rule + Why
→
Write to ctx_safety/
→
Update Boot Matrix

What each step does:

1

Write a Safety Rule (New Node)

Create a new file in ctx_safety/ containing three parts: Rule + Postmortem + Why. The postmortem describes how the fault unfolded, not as a formality, but so the agent understands why and can then judge edge cases on its own. Without a postmortem, an agent will work around a rule whenever a situation "seems reasonable."

2

Update the Glossary (Disambiguation)

If this time the meanings of "Preview Queue" and "Robot Controller Buffer" got confused, add a new disambiguation entry to GLOSSARY.md. Next time the agent encounters the word "queue," it won't confuse the two again.

3

Solidify the Decision in settled.md (Not Reversible)

If a decision is made that shouldn't be reopened for debate (such as "the resume point must be based on the actual TCP pose"), write it into settled.md. The agent will not propose a rejected approach again.

4

Update the Boot Matrix (Routing)

Ensure future tasks involving resumable pauses automatically load the new safety rule node.

5

Archive Old Documents (Don't Delete)

Move the old approach to _historical/ and tag it with superseded_by. Keep the history, since you may later need to know "why it was designed that way originally."

The point of solidifying: spend 10 minutes today writing a lesson into a node, and every related task in future benefits automatically. Not because you benefit (you might already remember it), but because the agent benefits. Every agent session starts from a blank slate; a solidified node is its only memory across sessions.

IV Anti-Patterns: Practices That Break the External Brain

Anti-patternConsequenceCorrect approach
Stuffing all information into CLAUDE.md Context window overflow, equivalent to forcing the external brain's contents back into working memory CLAUDE.md holds only "needed every time" principles; details go in the wiki, loaded on demand
Safety rules only say "don't do X," without the why The agent works around the rule in edge cases; the external brain's node lacks meaning and the connection breaks Rule + Why + Postmortem, as one unit
Terms left ambiguous Different sessions understand the same word differently; a knowledge network node name points to an uncertain meaning Group the Glossary by confusion scenario
No Truth Ladder When documents conflict, the agent picks one at random; equivalent to the external brain producing a contradictory memory An explicit priority ladder, so conflicts have a deterministic resolution
Treating working notes as authoritative An outdated approach in the Inbox gets treated as the current design The Inbox has very low authority on the Truth Ladder
Deleting old documents You lose the ability to trace back "why it was designed that way"; the knowledge network loses its historical dimension Move to _historical/ and tag with superseded_by

V Quick Start: Building an External Brain for Your Project

1

Write CLAUDE.md — the Behavioural Constitution

You don't need to cover everything at once. Start with behavioural principles (Think Before Coding, etc.) plus a first batch of hard rules (including the why). Add more as new rules come up.

2

Create the Wiki Skeleton

The 001-005 directory structure plus an INDEX.md for each directory. The initial content can be empty; set up the skeleton first, and let the content grow with the project.

3

Initialise the Agent Management Layer

Create four core files: GLOSSARY.md (the first batch of easily confused terms), TRUTH_LADDER.md (the priority ladder), BOOT_MATRIX.md (the routing table, which can start empty), and ctx_system_current.md (the current state of the system).

4

Keep Solidifying as Development Progresses

Fixed a bug → write a safety rule. Made a decision → write it to settled.md. Confused a term → add it to the Glossary. The wiki is a living knowledge network, not a one-off document.

The single most important thing: the most valuable nodes in the wiki aren't design documents, they're rules learned from failure. Every safety rule traces back to a real fault. An agent only truly follows a rule that came from a hard lesson, because it understands why.
