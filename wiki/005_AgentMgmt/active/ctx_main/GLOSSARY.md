# Glossary

Only terms that are easy to confuse or get subtly wrong. Not a full
robotics dictionary.

## 1. Kinematics direction

| Term | Definition | Notes |
|------|-----------|-------|
| **FK (Forward Kinematics)** | Joint angles → end-effector pose. One unique answer. | `docs/FR5_DH_Table.md`, implemented in `geometry_backend.py` |
| **IK (Inverse Kinematics)** | Target end-effector pose → joint angles. Up to 8 valid solutions for the FR5 (redundancy). | Implemented — `solve_ik`/`solve_ik_tcp` in `geometry_backend.py`; see `settled.md` S1.4/S1.5 |

## 2. Transform frames — the mesh-rendering trap

| Term | Definition | Notes |
|------|-----------|-------|
| **`T_0_i`** | Absolute DH transform: base frame → link *i* frame, at the *current* joint angles. | From `compute_fk()`, per `docs/FR5_DH_Table.md` |
| **`T_zero`** | `T_0_i` evaluated at `joints = [0,0,0,0,0,0]`. | Computed once at init |
| **Delta transform** | `Delta_i = T_0_i(q) @ inv(T_0_i(0))`. The *only* correct transform to apply to the OBJ mesh vertices. | See `docs/FR5_Mesh_Convention.md` — **do not** apply `T_0_i(q)` directly to mesh vertices, they already encode `T_0_i(0)`; direct application double-transforms and produces garbage geometry |

## 3. Points of interest

| Term | Definition | Notes |
|------|-----------|-------|
| **TCP (Tool Centre Point)** | The functional tip of whatever's mounted on the flange (here: the nozzle tip), not the flange centre itself. | Derived from `TCP_OFFSET_6D_MM_DEG`, transformed with `Delta_6`. **Not** `assets/printerHead/TCP.txt` since Stage 7.1 — that file is legacy, kept as a record; see `settled.md` S1.43 |
| **TCP offset** vs **User frame** | Two different 6D poses, both now real calibrated values rather than placeholders, and easy to confuse. The **TCP offset** is *flange-relative* — where the tool tip sits and how it is oriented relative to the mounting face (`[-134.777, 96.448, 106.334, 86.647, -13.136, 60.612]`, tool=1). The **User frame** is *base-relative* — where the workpiece origin sits in the world. One rides the arm; the other is fixed in the world. | `TCP_OFFSET_6D_MM_DEG` / `T_flange_to_tcp` vs `USER_FRAME_ORIGIN_MM` / `T_user_frame`; both `pose_to_matrix`-built, both from `docs/saved_coords_data_and_usage_EN.md` (§1.2 and §1.1) |
| **Flange** | The mounting face at the end of Link 6, where tools attach. | Frame = `T_0_6` |
| **Tool Axis** | Visual-only 2-node line from the flange origin to the TCP (196.91mm), standing in for the hidden `nozzle.obj`. Deliberately **not** a collision body — the tool's collision geometry is the single TCP point. | `TOOL_AXIS_COLOR`/`TOOL_AXIS_RADIUS_MM`, index 9 in `apply_delta_transform()`; see `settled.md` S1.43 |
| **Home position** | `[0, 0, 0, 0, 90, 0]` degrees — J5=90° points the tool straight down. | `docs/FR5_Joint_Limits.md` |
| **User frame** | A reference frame (position + rotation) from the base frame to a workpiece origin — here, the build-plate corner. Standard industrial-robot term (FANUC/UR/ABB all have one); Craig's *Introduction to Robotics* calls the same concept a **station frame**. Re-posable (position and XYZ fixed-angle rotation), stored as `self.T_user_frame`. Contrast the flange-relative **TCP offset** above. | `USER_FRAME_ORIGIN_MM` (`[-570, -300, -100]` since Stage 7.1 — the real tool's reach shift pushed the bed's far corner outside the envelope at the old `[-600, -300, 0]`), `load_build_plate()` in `geometry_backend.py`; see `settled.md` S1.2/S1.6/S1.43 |
| **G-code toolpath** | Preview curve of a parsed G-code file's `G1` (feed) moves, registered per "Load G-code preview" click (not live per-frame like the TCP trajectory). Does **not** auto-refresh when the build plate is repositioned — Move/Reset/Load Saved Position all require an explicit follow-up "Load G-code preview" click (S1.8's auto-reload was removed by S1.23). Modal position convention: an axis omitted from a line keeps its *last* value, not 0 — only the very first line defaults omitted axes to 0. `G0` (travel) moves update this modal position but are not drawn. | `parse_gcode()`/`load_gcode()`/`clear_gcode_preview()` in `geometry_backend.py`, loads `assets/models/planar/gcode/model.gcode` (fixed name every Cura export overwrites); see `settled.md` S1.3/S1.7/S1.8/S1.23 and `wiki/003_Guides/Gcode_Toolpath.md` |

## 4. Degrees of freedom

| Term | Definition | Notes |
|------|-----------|-------|
| **6DOF** | The FR5 has 6 revolute joints (J1–J6), giving 6 degrees of freedom — enough to reach any position *and* orientation in its workspace. | Distinguish from a 6DOF *pose* `[x,y,z,rx,ry,rz]`, which is the IK target format, not the joint count |

## 5. Toolpath execution — precompute, cache, playback

| Term | Definition | Notes |
|------|-----------|-------|
| **Toolpath IK precompute** | Solving IK for every G-code waypoint ahead of playback, chunked across frames (`PRECOMPUTE_CHUNK_SIZE` waypoints/call) so it doesn't block the GUI. Pausable/resumable/cancellable; aborts the whole precompute (no partial motion) at the first waypoint with no valid, ground-clearing branch. | `run_/step_/pause_/cancel_toolpath_ik_precompute()` in `geometry_backend.py`; result stored in `precompute_joint_path`; see `settled.md` S1.14/S1.15 |
| **Precompute disk cache** | Cross-session cache of a completed precompute, keyed on `{version, gcode_sha256, user_frame}` (G-code file content hash + build-plate pose, not mtime). A hit skips parsing and IK entirely. | `assets/models/planar/gcode/model.precompute.npz`, `save_/load_toolpath_precompute_cache()`, `_toolpath_cache_meta()`; see `settled.md` S1.21 |
| **`precompute_cache_meta`** | The cache key dict captured once, at precompute-start (or on a disk-cache hit) — used later to detect a plate move that invalidates the in-memory precompute mid-session, not just across sessions. | `geometry_backend.py`; see `settled.md` S1.22 |
| **Toolpath playback** | Driving the arm through `precompute_joint_path` while progressively revealing the printed bead mesh — beads start collapsed to zero-area (invisible) and are restored to their real vertex positions as `playback_index` crosses each bead's reveal point. | `run_/pause_/reset_/advance_toolpath_playback()` in `geometry_backend.py`; see `settled.md` S1.16 |
| **`playback_index` / `playback_running`** | Current waypoint index into `precompute_joint_path`, and whether playback is actively advancing. `playback_index` persists across pause; only `reset_toolpath_playback()` zeroes it. Indexes `precompute_joint_path` directly, so both must be reset together whenever that list is discarded (`_reset_toolpath_playback_state()`) — a stale index into an emptied path was the project's one confirmed GUI crash bug (fixed; see `settled.md` S1.24). | `geometry_backend.py` |
| **`PLAYBACK_RENDER_STRIDE` / `PLAYBACK_LOOKAHEAD_BEADS`** | Two independent render-cost throttles: the first limits how often playback pushes a Polyscope update (vs. every step); the second limits how far ahead of actual progress the registered bead mesh is grown, so registered mesh size — not just push frequency — tracks progress. | `geometry_backend.py`; see `settled.md` S1.17–S1.20 |

## 6. Curved-surface routing — geodesics

| Term | Definition | Notes |
|------|-----------|-------|
| **Geodesic** | Here, specifically: the shortest path between two points that stays **on** a print surface, computed by Dijkstra over the surface mesh's edge graph. It is a polyline of mesh vertices, not a smooth curve — the true continuous geodesic can cut across triangle faces, this one is constrained to edges. Used for travel moves between disjoint curve pieces, so the nozzle hugs the shoulder mockup instead of chording through it. | `dijkstra_surface()`/`geodesic_path_nodes()` in `geometry_backend.py`; see `settled.md` S1.31 and `wiki/003_Guides/CurvedModel_Geodesics.md` |
| **Snap node** | The mesh vertex a curve endpoint is snapped to, since endpoints sit ~0.5 mm *off* their surface rather than exactly on a vertex. Measured max snap error 0.684 mm, inside the ~1.24 mm median mesh edge. Distinct endpoints often share a snap node — 58 unique nodes for RX's 70 endpoints, 55 for TX's — which is why the run is 113 Dijkstras and not 140. | `nearest_vertex_index()`, `geodesic_snap_nodes`; see `settled.md` S1.31 |
| **Endpoint index** | Index into a layer's 70×70 geodesic cost matrix. Endpoint `2p` is `pieces[p][0]` and `2p+1` is `pieces[p][-1]`, so the matrix is indexed by *endpoint*, not by piece — and choosing which end of piece `p` to enter from is a choice between rows `2p` and `2p+1`. | `_layer_endpoints_world()`; see `settled.md` S1.31 |
| **Cost-matrix zero** | `cost[i][j] == 0.0` for `i != j` means endpoints `i` and `j` snapped to the **same** vertex. Legitimate and common. Mind the counting convention: the matrix is symmetric, so one endpoint *pair* is two *entries*. As entries — RX 24 off-diagonal (16 from different pieces = 8 pairs, 8 from one piece's own ends = 4 pieces); TX 30 (18 = 9 pairs, 12 = 6 pieces). Roadmap 6.3's ordering therefore faces many tied zero-cost moves, and a closed loop's `cost[2p][2p+1] == 0.0` must not be read as free travel to a different place. | See `settled.md` S1.31 |
| **Abutting pieces** | Separate curve pieces whose ends lie sub-millimetre apart — 16 RX / 18 TX endpoints are within 0.5mm of another piece's line. Because all 35 pieces of a layer render as one combined curve network, the join is invisible, so a geodesic ending at a genuine piece end looks like it stops halfway along a curve. Same phenomenon as the different-piece cost-matrix zeros, counted as endpoints rather than pairs. | `_register_curve_layer()`; see `settled.md` S1.31 |
| **Snap gap** | A geodesic starts and ends at the *snapped mesh vertex*, not the curve endpoint — median ~0.36mm, max 0.68mm away. So a travel move built from path nodes alone doesn't quite meet the piece it connects. **6.3 closes it** by bookending each travel polyline with the true curve endpoints (lifted to hover height). | `geodesic_path_nodes()`, `build_print_order()`; see `settled.md` S1.31, S1.35 |

## 7. Curved-surface printing — layers and passes

| Term | Definition | Notes |
|------|-----------|-------|
| **RX layer / TX layer** | The two electrode layers of the printed capacitive sensor, offset from each other by the print's thickness. RX (receive) travels on `Surface_RX_Offset`, TX (transmit) on `Surface_TX_Base`. The physical stack is **BOT → RX (2.00mm) → TX (4.02mm)**, so RX is the layer nearer the shoulder mockup. ⚠ `Surface_TX_Base`'s name reads as "the base layer" but TX is the *outer* one — the filename is the misleading signal here, the measurement was right. | `CURVED_LAYERS` in `examples/curved_surface_printing/study_config.py`; see `settled.md` S1.30, S1.32, S1.33 |
| **Pass** | One robot-driven print of a *single* layer, start to finish. **RX is the first pass, TX the second.** Each pass has its own toolpath, cost matrix, print order, precompute run, cache file and playback — nothing spans both, and there is no travel move from the last RX piece to the first TX piece. | See `settled.md` S1.32 |
| **Silicone base layer** | Applied to the shoulder mockup **before** the RX pass — confirmed by the supervisor. `Surface_RX_Offset` is this base layer's outer surface, not the bare shoulder body, which is what the measured 2.00mm gap between `Surface_Bot` and `Surface_RX_Offset` turned out to be. Distinct from "Silicone fill" below (that's *between* passes; this is *before* the first one). | See `settled.md` S1.34 |
| **Silicone fill** | The **manual** step between the passes: after RX prints, its gaps are filled with silicone by hand; the same again after TX. This is why the passes never merge — a human works on the part in between. **Not modelled in the simulator**; switching the live layer is the user action that stands in for it. It also doubles as the sensor's dielectric, which corroborates the capacitive reading. | See `settled.md` S1.32 |
| **Live layer** | The layer currently selected in the GUI (the non-`Planar` entries of the **Toolpath source** selector). It scopes *everything* downstream — ordering, hover surface, normals, precompute, cache file, playback — and drives scene visibility. **Functional, not cosmetic** — `Surface_RX_Offset` is sealed inside the `Surface_TX_Base` shell, so RX is *invisible* with TX_Base shown. Visibility follows the **S1.32 physical stack** (`i <= layer`): RX's view shows RX + below; TX's view shows the whole object incl. the printed RX beneath (6.6/S1.38 — replaced 6.3's provisional strict isolation). | `apply_live_layer_visibility()`; see `settled.md` S1.32, S1.35, **S1.38** |
| **Print order** | The sequence in which a layer's 35 pieces are printed, chosen to minimise total inter-piece travel — a TSP variant where each piece has two entry ends. Seeded by a greedy nearest-endpoint chain, improved by 2-opt over oriented pieces (segment reversal flips entry/exit ends; valid because cost is symmetric). Stored as a list of `(piece, entry_end)`. Feed cost is order-invariant, so travel-sum is the whole objective. | `greedy_piece_order()`/`two_opt()`/`build_print_order()`; see `settled.md` S1.35 |
| **Travel move** | The non-printing hop between two pieces: the 6.2 geodesic offset outward along the surface normal by the **hover clearance** (`CURVED_TRAVEL_HOVER_MM` = 4mm) so the nozzle clears the mockup and wet traces, bookended with the true curve endpoints (snap-gap closure). Rendered a solid warm red (`CURVED_TRAVEL_COLOR`), deliberately off the print-order gradient ramp so "printing" vs "moving" read apart. | `build_print_order()`; see `settled.md` S1.35 |
| **Print-order overlay** | The `Curved Order Feed <name>` curve network drawn over a layer's printed pieces *in print order*, coloured by a **sequence gradient** (piece 1 dark → piece N bright, the `CURVED_ORDER_CMAP` ramp via per-edge `add_color_quantity`) so the order itself is legible, not just coverage. Each piece is oriented by its entry end. Supersedes the flat base curve when shown. | `build_print_order()`, `_sequence_colors()`; see `settled.md` S1.35 |
| **Live-layer isolation** | How the GUI scopes scene visibility to the live layer: since 6.6 (S1.38) it shows layer *k* **plus every layer beneath it** in the physical stack (`i <= layer`) — picking RX enables only RX + below and hides TX; picking TX shows the whole object incl. the printed RX beneath. Replaced 6.3's provisional *strict* one-at-a-time isolation. | `apply_live_layer_visibility()`; see `settled.md` S1.32, S1.35, **S1.38** |
| **Toolpath source** | Which toolpath the *one shared* set of Run/Pause/Cancel Precompute + Run/Pause/Reset Toolpath controls currently targets — `toolpath_source` = `-1` (planar G-code) or a curved layer index. The GUI's "Toolpath Source" selector sets it; the controls dispatch on it (no duplicated curved control set). A **layer-mixup guard** force-cancels a paused run of a *different* source rather than silently resuming it, keyed on `precompute_cache_path`. | `run_active_toolpath_ik_precompute()`, source-aware `*_toolpath_playback()`; see `settled.md` **S1.38** |
| **Plate plane** | The posed build plate modelled as an **infinite** plane for clearance, derived live from `T_user_frame`: point = plate origin lifted `PLATE_THICKNESS_MM` along local +Z (the top/print face), normal = plate local +Z. A vertex clears iff `(world − point) · normal ≥ −tol`. Replaces the old world-z=0 proxy. Note the default plate pose rejects early (the arm reaches below the plate); the plate is repositioned lower for the print (see the supervisor's print-setup docs). | `_plate_plane()`; see `settled.md` **S1.40** |
| **TCP-through-plate toggle** | The "Allow TCP through build plate" checkbox — `allow_tcp_through_plate`, default **OFF** (roadmap 6.8, replaced the old `reject_below_ground`). The 6 arm-link meshes (0–5) are **always** rejected below the plate plane; the nozzle (mesh 6) is rejected too unless this is ON. Applies to both paths; the curved tangent-plane nozzle check (S1.37) still layers on top. Folded into the precompute cache key (it changes which IK branch is accepted), `PRECOMPUTE_CACHE_VERSION` 3→4. Note the inverted sense vs the old toggle: OFF is now the *strict* (safe) default. | `_branch_clears_ground()`/`_meshes_clear_plane()`; see `settled.md` **S1.40**, S1.37 |
| **Surface normal (outward)** | Per-vertex surface normal, computed from scratch in numpy (`compute_vertex_normals` — trimesh's needs scipy and degrades without it) and oriented **away from `Surface_Bot`** by a global majority vote at load time, so the sign is baked into `curved_surface_vnormals_world`. Outward = the hover direction; a wrong sign drives the nozzle into the mockup. Introduced in 6.3 for hover; 6.4 reuses it for per-waypoint orientation. | `compute_vertex_normals()`/`_orient_normals_outward()`; see `settled.md` S1.35 |
| **Orientation frame (per-waypoint)** | The target TCP orientation at one printed feed point, holding the nozzle perpendicular to the curved surface — a 3×3 `R_target` whose **Z axis is the outward surface normal** (nozzle approaches along −Z) and whose in-plane X/Y are pinned to a **fixed world reference**, *not* the path tangent (the nozzle is rotationally symmetric, so the spin DOF is free and is fixed to keep the arm from spinning as the path meanders). Per layer, stored as `curved_orient_frames` — a list of `(pos_world, R_target)` in print order, the array 6.5 fed to IK (`run_curved_toolpath_ik_precompute`). Drawn as a downsampled XYZ triad overlay (`Curved Orient Frames <name>`). Supersedes the flat-plate single constant `R_target` (S1.12). ⚠ **Defective since 6.4, found by 7.2:** the "fixed world reference" is picked per waypoint by `argmin(\|world_axes @ z\|)`, which switches **discretely** as the normal sweeps — spinning the commanded frame about its own Z and making curved jobs fail the spec's joint-step row (23/35 RX, 15/35 TX). Guarding against the projection *collapsing* is not the same as keeping the choice *continuous*. Open, fix sequenced with 7.3. | `build_orientation_frames()`; see `settled.md` S1.36, S1.37 (clearance half superseded by **S1.44**), and `wiki/001_Inbox/2026-08-15_orientation_frame_flips_row5.md` |
| **Rim-hugging** | A geodesic (and thus a travel move) can legitimately track a print surface's open boundary, since going around a dome's rim can be the shortest surface path. Mean ~18% of nodes over random pairs, but up to ~46% on *ordered* travel moves (greedy favours short near-rim hops). Geometrically correct; reported in `build_print_order()`'s status as a physical-plausibility flag for 6.4/6.5, not a hard reject. | `_surface_boundary_vertices()`; see `settled.md` S1.31, S1.35 |

## 8. Export and rejection criteria (Stage 7)

| Term | Definition | Notes |
|------|-----------|-------|
| **Segment** | The exchange spec's unit of export: **one continuous extrusion line**. On both toolpath sources it is exactly a maximal run of consecutive `is_feed_move` waypoints — for curved that reproduces one Stage 6.3 print-order piece (verified: 35 segments == 35 pieces on both layers), for planar a G1 run bounded by G0 travels. Travel runs are **dropped, not exported**: the receiving side re-inserts a travel MoveJ between adjacent segments. One shared builder, not two — the piece boundaries are already encoded in the feed flags. | `build_export_segments()`; see `settled.md` **S1.44** |
| **Rejection Criteria** | The exchange spec's seven-row table defining a valid print job, implemented verbatim: identity check, TCP offset vs calibration, joint limits, per-point FK, joint step within a segment, `num_points` consistency, and `\|J5\| < 2°`. The first six **REJECT**; the last only **WARNs**. ⚠ They validate **data, not geometry** — a job can pass all seven and still drive the arm through the plate or the workpiece. Applies to **both** toolpath sources (nothing in the rows is curved- or study-specific); the *collision narrowing* of 7.2 is the asymmetric half, curved-only. | `validate_job()`; see `settled.md` **S1.44** |
| **Identity check** | Row 1, and the most fundamental: `FK([0]*6)` + `T_flange_to_tcp` must reproduce the spec's published zero-pose TCP 6D pose `[-954.777, -308.334, 146.448, -161.378, -58.051, -25.434]` within 0.1mm / 0.5°. If it fails, the DH table, the rotation convention or the tool offset is wrong and nothing downstream is trustworthy. Measures **0.000000mm / 0.0003°** today. Only meaningful once 7.1's real offset is wired in — which is why the criteria could not lead Stage 7. | `validate_job()`; see `settled.md` S1.43, **S1.44** |
| **Physical vs practical joint limits** | Two different things from the same doc, not interchangeable. **Physical** (`geometry_backend.PHYSICAL_JOINT_LIMITS`, J2/J4 −264…+84) is the robot's real envelope and feeds every **solver** call plus the spec's row 3. **Practical** (`gui_panel.JOINT_LIMITS`, J2 −130…+80) is a deliberately conservative hand-driving range and governs the **sliders only**. Until 7.2 the solver borrowed the slider constant and rejected reachable poses — 425 valid branches vs 207 over an 80-pose sample. J2's shallow floor is a hand-rolled collision proxy, which matters because there is no mesh-vs-mesh collision anywhere. | `docs/FR5_Joint_Limits.md`; see `settled.md` **S1.44** |
| **`check_collision`** | The single boolean that is the whole planar/curved difference in the precompute since 7.2 (it replaced `tip_tolerance_mm`, which had been the same discriminator). **True** (planar) keeps Stage 6.8's posed-plate rejection; **False** (curved) drops it, leaving the Rejection Criteria as the only definition of a bad job. Snapshotted per run at `_begin_toolpath_precompute` rather than read from `toolpath_source`, which could mutate mid-solve. Resets to True on abort — the checked direction. | `_begin_toolpath_precompute()`/`step_toolpath_ik_precompute()`; see `settled.md` **S1.44** |
